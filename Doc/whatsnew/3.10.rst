.. _whatsnew310-pep563:

Context manager trong dấu ngoặc
-------------------------------

Giờ đây, có thể sử dụng dấu ngoặc bao quanh để tiếp tục câu lệnh trên nhiều dòng trong context manager. Điều này cho phép định dạng một nhóm dài các context manager trên nhiều dòng, tương tự như cách trước đây có thể làm với các câu lệnh import. Ví dụ, tất cả các ví dụ sau đây hiện đều hợp lệ:

.. code-block:: python

    with (CtxManager() as example):
        ...

    with (
        CtxManager1(),
        CtxManager2()
    ):
        ...

    with (CtxManager1() as example,
          CtxManager2()):
        ...

    with (CtxManager1(),
          CtxManager2() as example):
        ...

    with (
        CtxManager1() as example1,
        CtxManager2() as example2
    ):
        ...

cũng có thể sử dụng dấu phẩy ở cuối nhóm được bao quanh:

.. code-block:: python

    with (
        CtxManager1() as example1,
        CtxManager2() as example2,
        CtxManager3() as example3,
    ):
        ...

Cú pháp mới này sử dụng các khả năng không phải LL(1) của parser mới. Hãy xem :pep:`617` để biết thêm chi tiết.

(Được đóng góp bởi Guido van Rossum, Pablo Galindo và Lysandros Nikolaou trong :issue:`12782` và :issue:`40334`.)


Thông báo lỗi tốt hơn
---------------------

Lỗi cú pháp
~~~~~~~~~~~

Khi phân tích cú pháp mã có chứa dấu ngoặc tròn hoặc dấu ngoặc vuông chưa đóng, interpreter hiện sẽ bao gồm vị trí của dấu ngoặc chưa đóng thay vì hiển thị *SyntaxError: unexpected EOF while parsing* hoặc trỏ đến một vị trí không chính xác nào đó. Ví dụ, hãy xem đoạn mã sau (lưu ý dấu '{' chưa đóng):

.. code-block:: python

    expected = {9: 1, 18: 2, 19: 2, 27: 3, 28: 3, 29: 3, 36: 4, 37: 4,
                38: 4, 39: 4, 45: 5, 46: 5, 47: 5, 48: 5, 49: 5, 54: 6,
    some_other_code = foo()

Các phiên bản trước của interpreter báo cáo những vị trí gây nhầm lẫn là vị trí xảy ra lỗi cú pháp:

.. code-block:: python

   File "example.py", line 3
       some_other_code = foo()
                       ^
   SyntaxError: invalid syntax

nhưng trong Python 3.10, một lỗi cung cấp nhiều thông tin hơn sẽ được phát ra:

.. code-block:: python

    File "example.py", line 1
        expected = {9: 1, 18: 2, 19: 2, 27: 3, 28: 3, 29: 3, 36: 4, 37: 4,
                   ^
    SyntaxError: '{' was never closed


Tương tự, các lỗi liên quan đến literal chuỗi chưa được đóng (dùng dấu nháy đơn và dấu nháy ba) giờ đây sẽ trỏ đến phần bắt đầu của chuỗi thay vì báo EOF/EOL.

Những cải tiến này được lấy cảm hứng từ công trình trước đây trong trình thông dịch PyPy.

(Đóng góp của Pablo Galindo trong :issue:`42864` và Batuhan Taskaya trong
:issue:`40176`.)

:exc:`SyntaxError` do trình thông dịch phát sinh giờ đây sẽ đánh dấu toàn bộ phạm vi lỗi của biểu thức tạo thành chính lỗi cú pháp, thay vì chỉ đánh dấu vị trí phát hiện vấn đề. Theo cách này, thay vì hiển thị (trước Python 3.10):

.. code-block:: python

    >>> foo(x, z for z in range(10), t, w)
      File "<stdin>", line 1
        foo(x, z for z in range(10), t, w)
               ^
    SyntaxError: Generator expression must be parenthesized

giờ đây Python 3.10 sẽ hiển thị exception như sau:

.. code-block:: python

    >>> foo(x, z for z in range(10), t, w)
      File "<stdin>", line 1
        foo(x, z for z in range(10), t, w)
               ^^^^^^^^^^^^^^^^^^^^
    SyntaxError: Generator expression must be parenthesized

Cải tiến này do Pablo Galindo đóng góp trong :issue:`43914`.

Một lượng đáng kể các thông báo chuyên biệt mới dành cho các exception :exc:`SyntaxError` đã được bổ sung. Một số thông báo đáng chú ý nhất như sau:

* Thiếu ``:`` trước các khối:

  .. code-block:: python

      >>> if rocket.position > event_horizon
        File "<stdin>", line 1
          if rocket.position > event_horizon
                                            ^
      SyntaxError: expected ':'

  (Do Pablo Galindo đóng góp trong :issue:`42997`.)

* Các tuple không có dấu ngoặc đơn trong các đích của comprehension:

  .. code-block:: python

      >>> {x,y for x,y in zip('abcd', '1234')}
        File "<stdin>", line 1
          {x,y for x,y in zip('abcd', '1234')}
           ^
      SyntaxError: did you forget parentheses around the comprehension target?

  (Do Pablo Galindo đóng góp trong :issue:`43017`.)

* Thiếu dấu phẩy trong các literal tập hợp và giữa các biểu thức:

  .. code-block:: python

      >>> items = {
      ... x: 1,
      ... y: 2
      ... z: 3,
        File "<stdin>", line 3
          y: 2
             ^
      SyntaxError: invalid syntax. Perhaps you forgot a comma?

  (Do Pablo Galindo đóng góp trong :issue:`43822`.)

* Nhiều kiểu Exception không có dấu ngoặc đơn:

  .. code-block:: python

      >>> try:
      ...     build_dyson_sphere()
      ... except NotEnoughScienceError, NotEnoughResourcesError:
        File "<stdin>", line 3
          except NotEnoughScienceError, NotEnoughResourcesError:
                 ^
      SyntaxError: multiple exception types must be parenthesized

  (Do Pablo Galindo đóng góp trong :issue:`43149`.)

* Thiếu ``:`` và các giá trị trong các dictionary literal:

  .. code-block:: python

      >>> values = {
      ... x: 1,
      ... y: 2,
      ... z:
      ... }
        File "<stdin>", line 4
          z:
           ^
      SyntaxError: expression expected after dictionary key and ':'

      >>> values = {x:1, y:2, z w:3}
        File "<stdin>", line 1
          values = {x:1, y:2, z w:3}
                              ^
      SyntaxError: ':' expected after dictionary key

  (Do Pablo Galindo đóng góp trong :issue:`43823`.)

* Các khối ``try`` không có khối ``except`` hoặc ``finally``:

  .. code-block:: python

      >>> try:
      ...     x = 2
      ... something = 3
        File "<stdin>", line 3
          something  = 3
          ^^^^^^^^^
      SyntaxError: expected 'except' or 'finally' block

  (Do Pablo Galindo đóng góp trong :issue:`44305`.)

* Sử dụng ``=`` thay vì ``==`` trong các phép so sánh:

  .. code-block:: python

      >>> if rocket.position = event_horizon:
        File "<stdin>", line 1
          if rocket.position = event_horizon:
                             ^
      SyntaxError: cannot assign to attribute here. Maybe you meant '==' instead of '='?

  (Do Pablo Galindo đóng góp trong :issue:`43797`.)

* Cách sử dụng ``*`` trong f-strings:

  .. code-block:: python

      >>> f"Black holes {*all_black_holes} and revelations"
        File "<stdin>", line 1
          (*all_black_holes)
           ^
      SyntaxError: f-string: cannot use starred expression here

  (Do Pablo Galindo đóng góp trong :issue:`41064`.)

IndentationErrors
~~~~~~~~~~~~~~~~~

Nhiều ngoại lệ :exc:`IndentationError` hiện cung cấp thêm ngữ cảnh về loại khối nào đang yêu cầu thụt lề, bao gồm cả vị trí của câu lệnh:

.. code-block:: python

    >>> def foo():
    ...    if lel:
    ...    x = 2
      File "<stdin>", line 3
        x = 2
        ^
    IndentationError: expected an indented block after 'if' statement in line 2


AttributeErrors
~~~~~~~~~~~~~~~

Khi in :exc:`AttributeError`, :c:func:`!PyErr_Display` sẽ đưa ra các đề xuất về những tên thuộc tính tương tự trong đối tượng nơi ngoại lệ được phát sinh:

.. code-block:: python

    >>> collections.namedtoplo
    Traceback (most recent call last):
      File "<stdin>", line 1, in <module>
    AttributeError: module 'collections' has no attribute 'namedtoplo'. Did you mean: namedtuple?

(Do Pablo Galindo đóng góp trong :issue:`38530`.)

.. warning::
   Lưu ý rằng cách này sẽ không hoạt động nếu :c:func:`!PyErr_Display` không được gọi để hiển thị lỗi, điều này có thể xảy ra nếu một hàm hiển thị lỗi tùy chỉnh khác được sử dụng. Đây là tình huống phổ biến trong một số REPL như IPython.

NameErrors
~~~~~~~~~~

Khi in :exc:`NameError` do interpreter phát sinh, :c:func:`!PyErr_Display` sẽ đưa ra các đề xuất về những tên biến tương tự trong hàm nơi ngoại lệ được phát sinh:

.. code-block:: python

    >>> schwarzschild_black_hole = None
    >>> schwarschild_black_hole
    Traceback (most recent call last):
      File "<stdin>", line 1, in <module>
    NameError: name 'schwarschild_black_hole' is not defined. Did you mean: schwarzschild_black_hole?

(Được đóng góp bởi Pablo Galindo trong :issue:`38530`.)

PEP 626 cung cấp số dòng chính xác và đáng tin cậy hơn cho các công cụ gỡ lỗi, profiling và đo độ bao phủ. Các sự kiện tracing, với số dòng chính xác, được tạo cho mọi dòng mã được thực thi và chỉ cho những dòng mã được thực thi.

:meth:`~codeobject.co_lines` thay vào đó.

PEP 634: Đối sánh mẫu cấu trúc
------------------------------

Đối sánh mẫu cấu trúc đã được bổ sung dưới dạng *câu lệnh match* và *các câu lệnh case* với các hành động liên kết. Các mẫu bao gồm các sequence, mapping, kiểu dữ liệu nguyên thủy cũng như các instance của class. Đối sánh mẫu cho phép chương trình trích xuất thông tin từ các kiểu dữ liệu phức tạp, rẽ nhánh dựa trên cấu trúc dữ liệu và áp dụng các hành động cụ thể dựa trên các dạng dữ liệu khác nhau.

Cú pháp và các phép toán
~~~~~~~~~~~~~~~~~~~~~~~~

Cú pháp tổng quát của pattern matching là::

      match subject:
          case <pattern_1>:
              <action_1>
          case <pattern_2>:
              <action_2>
          case <pattern_3>:
              <action_3>
          case _:
              <action_wildcard>

Một câu lệnh match nhận một biểu thức và so sánh giá trị của biểu thức đó với các pattern liên tiếp được cung cấp dưới dạng một hoặc nhiều khối case. Cụ thể, pattern matching hoạt động bằng cách:

1. sử dụng dữ liệu có kiểu và hình dạng (``subject``)
2. đánh giá ``subject`` trong câu lệnh ``match``
3. so sánh subject với từng pattern trong câu lệnh ``case`` từ trên xuống dưới cho đến khi xác nhận được một kết quả khớp.
4. thực thi hành động liên kết với pattern của kết quả khớp đã xác nhận
5. Nếu không xác nhận được kết quả khớp chính xác, case cuối cùng, một ``_`` wildcard, nếu được cung cấp, sẽ được dùng làm case khớp. Nếu không xác nhận được kết quả khớp chính xác và không tồn tại wildcard case, toàn bộ khối match sẽ không thực hiện thao tác nào.

Cách tiếp cận khai báo
~~~~~~~~~~~~~~~~~~~~~~

Người đọc có thể đã biết về pattern matching thông qua ví dụ đơn giản về việc so khớp một subject (đối tượng dữ liệu) với một literal (mẫu) bằng câu lệnh switch trong C, Java hoặc JavaScript (và nhiều ngôn ngữ khác). Câu lệnh switch thường được dùng để so sánh một đối tượng/biểu thức với các câu lệnh case chứa các literal.

Có thể tìm thấy những ví dụ mạnh mẽ hơn về pattern matching trong các ngôn ngữ như Scala và Elixir. Với structural pattern matching, cách tiếp cận này mang tính "khai báo" (declarative) và nêu rõ các điều kiện (các pattern) để dữ liệu khớp.

Mặc dù có thể sử dụng một chuỗi hướng dẫn "mệnh lệnh" (imperative) gồm các câu lệnh "if" lồng nhau để thực hiện điều tương tự như structural pattern matching, cách này kém rõ ràng hơn so với cách tiếp cận "khai báo". Thay vào đó, cách tiếp cận "khai báo" nêu rõ các điều kiện cần đáp ứng để khớp và dễ đọc hơn nhờ các pattern tường minh. Mặc dù structural pattern matching có thể được dùng ở dạng đơn giản nhất để so sánh một biến với một literal trong câu lệnh case, giá trị thực sự của nó đối với Python nằm ở khả năng xử lý kiểu và hình dạng của subject.

Pattern đơn giản: khớp với một literal
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Hãy xem ví dụ này dưới dạng đơn giản nhất của pattern matching: một giá trị, subject, được so khớp với nhiều literal, tức các pattern. Trong ví dụ dưới đây, ``status`` là subject của câu lệnh match. Các pattern là từng câu lệnh case, trong đó các literal biểu diễn mã trạng thái của request. Hành động tương ứng với case sẽ được thực thi sau khi khớp::

    def http_error(status):
        match status:
            case 400:
                return "Bad request"
            case 404:
                return "Not found"
            case 418:
                return "I'm a teapot"
            case _:
                return "Something's wrong with the internet"

Nếu hàm trên được truyền một ``status`` có giá trị 418, "I'm a teapot" sẽ được trả về. Nếu hàm trên được truyền một ``status`` có giá trị 500, câu lệnh case có ``_`` sẽ khớp như một wildcard, và "Something's wrong with the internet" sẽ được trả về. Lưu ý khối cuối cùng: tên biến, ``_``, hoạt động như một *wildcard* và bảo đảm subject luôn khớp. Việc sử dụng ``_`` là tùy chọn.

Bạn có thể kết hợp nhiều literal trong một pattern duy nhất bằng ``|`` ("hoặc")::

            case 401 | 403 | 404:
                return "Not allowed"

Hành vi khi không có wildcard
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Nếu sửa đổi ví dụ trên bằng cách xóa block case cuối cùng, ví dụ sẽ trở thành::

    def http_error(status):
        match status:
            case 400:
                return "Bad request"
            case 404:
                return "Not found"
            case 418:
                return "I'm a teapot"

Nếu không sử dụng ``_`` trong câu lệnh case, có thể sẽ không có kết quả khớp. Nếu không có kết quả khớp, hành vi sẽ là no-op. Ví dụ, nếu ``status`` 500 được truyền vào, một no-op sẽ xảy ra.

Pattern với literal và biến
~~~~~~~~~~~~~~~~~~~~~~~~~~~

Pattern có thể trông giống như phép gán unpacking và có thể được dùng để liên kết các biến. Trong ví dụ này, một điểm dữ liệu có thể được unpack thành tọa độ x và tọa độ y::

    # point is an (x, y) tuple
    match point:
        case (0, 0):
            print("Origin")
        case (0, y):
            print(f"Y={y}")
        case (x, 0):
            print(f"X={x}")
        case (x, y):
            print(f"X={x}, Y={y}")
        case _:
            raise ValueError("Not a point")

Pattern đầu tiên có hai literal, ``(0, 0)``, và có thể được xem là phần mở rộng của pattern literal ở trên. Hai pattern tiếp theo kết hợp một literal và một biến, trong đó biến *liên kết* một giá trị từ subject (``point``). Pattern thứ tư lấy ra hai giá trị, khiến nó tương tự về mặt khái niệm với phép gán unpacking ``(x, y) = point``.

Mẫu và class
~~~~~~~~~~~~

Nếu bạn sử dụng các class để cấu trúc dữ liệu, bạn có thể dùng tên class theo sau là danh sách đối số tương tự như một constructor làm mẫu. Mẫu này có khả năng ghi nhận các thuộc tính của instance vào các biến::

    class Point:
        def __init__(self, x, y):
            self.x = x
            self.y = y

    def location(point):
        match point:
            case Point(x=0, y=0):
                print("Origin is the point's location.")
            case Point(x=0, y=y):
                print(f"Y={y} and the point is on the y-axis.")
            case Point(x=x, y=0):
                print(f"X={x} and the point is on the x-axis.")
            case Point():
                print("The point is located somewhere else on the plane.")
            case _:
                print("Not a point")

Mẫu với tham số vị trí
^^^^^^^^^^^^^^^^^^^^^^

Bạn có thể sử dụng tham số vị trí với một số class dựng sẵn cung cấp thứ tự cho các thuộc tính của chúng (ví dụ: dataclasses). Bạn cũng có thể xác định vị trí cụ thể cho các thuộc tính trong mẫu bằng cách thiết lập thuộc tính đặc biệt ``__match_args__`` trong các class của mình. Nếu thuộc tính này được đặt thành ("x", "y"), các mẫu sau đều tương đương (và đều liên kết thuộc tính ``y`` với biến ``var``)::

    Point(1, var)
    Point(1, y=var)
    Point(x=1, y=var)
    Point(y=var, x=1)

Mẫu lồng nhau
~~~~~~~~~~~~~

Các mẫu có thể được lồng nhau tùy ý. Ví dụ: nếu dữ liệu của chúng ta là một danh sách ngắn các điểm, danh sách này có thể được đối sánh như sau::

    match points:
        case []:
            print("No points in the list.")
        case [Point(0, 0)]:
            print("The origin is the only point in the list.")
        case [Point(x, y)]:
            print(f"A single point {x}, {y} is in the list.")
        case [Point(0, y1), Point(0, y2)]:
            print(f"Two points on the Y axis at {y1}, {y2} are in the list.")
        case _:
            print("Something else is found in the list.")

Mẫu phức tạp và wildcard
~~~~~~~~~~~~~~~~~~~~~~~~

Cho đến đây, các ví dụ chỉ sử dụng ``_`` trong câu lệnh case cuối cùng. Có thể sử dụng ký tự đại diện trong các mẫu phức tạp hơn, chẳng hạn như ``('error', code, _)``. Ví dụ::

   match test_variable:
       case ('warning', code, 40):
           print("A warning has been received.")
       case ('error', code, _):
           print(f"An error {code} occurred.")

Trong trường hợp trên, ``test_variable`` sẽ khớp với ('error', code, 100) và ('error', code, 800).

Guard
~~~~~

Chúng ta có thể thêm mệnh đề ``if`` vào một mẫu, được gọi là "guard". Nếu guard là false, ``match`` sẽ tiếp tục thử khối case tiếp theo. Lưu ý rằng việc bắt giá trị diễn ra trước khi guard được đánh giá::

    match point:
        case Point(x, y) if x == y:
            print(f"The point is located on the diagonal Y=X at {x}.")
        case Point(x, y):
            print(f"Point is not on the diagonal.")

Các tính năng chính khác
~~~~~~~~~~~~~~~~~~~~~~~~

Một số tính năng chính khác:

- Giống như phép gán unpacking, các mẫu tuple và list có cùng ý nghĩa và thực sự khớp với các sequence tùy ý. Về mặt kỹ thuật, subject phải là một sequence. Do đó, một ngoại lệ quan trọng là các mẫu không khớp với iterator. Ngoài ra, để ngăn ngừa một lỗi thường gặp, các mẫu sequence không khớp với string.

- Các mẫu chuỗi hỗ trợ wildcard: ``[x, y, *rest]`` và ``(x, y, *rest)`` hoạt động tương tự như wildcard trong phép gán unpacking. Tên sau ``*`` cũng có thể là ``_``, vì vậy ``(x, y, *_)`` khớp với một chuỗi gồm ít nhất hai mục mà không liên kết các mục còn lại.

- Mẫu ánh xạ: ``{"bandwidth": b, "latency": l}`` thu thập các giá trị ``"bandwidth"`` và ``"latency"`` từ một dict. Không giống các mẫu chuỗi, các key bổ sung sẽ bị bỏ qua. Wildcard ``**rest`` cũng được hỗ trợ. (Tuy nhiên, ``**_`` sẽ là dư thừa nên không được phép.)

- Các mẫu con có thể được thu thập bằng từ khóa ``as``::

      case (Point(x1, y1), Point(x2, y2) as p2): ...

  This binds x1, y1, x2, y2 like you would expect without the ``as`` clause,
  and p2 to the entire second item of the subject.

- Hầu hết các literal được so sánh bằng phép so sánh bằng nhau. Tuy nhiên, các singleton ``True``, ``False`` và ``None`` được so sánh bằng identity.

- Có thể sử dụng các hằng số có tên trong mẫu. Các hằng số có tên này phải là tên có dấu chấm để tránh việc hằng số bị diễn giải thành biến capture::

      from enum import Enum
      class Color(Enum):
          RED = 0
          GREEN = 1
          BLUE = 2

      color = Color.GREEN
      match color:
          case Color.RED:
              print("I see red!")
          case Color.GREEN:
              print("Grass is green")
          case Color.BLUE:
              print("I'm feeling the blues :(")

Để xem đặc tả đầy đủ, hãy tham khảo :pep:`634`. Phần động cơ và lý do được trình bày trong :pep:`635`, còn hướng dẫn dài hơn nằm trong :pep:`636`.

Tùy chọn ``EncodingWarning`` và ``encoding="locale"`` tùy chọn
--------------------------------------------------------------

Mã hóa mặc định của :class:`~io.TextIOWrapper` và :func:`open` phụ thuộc vào nền tảng và locale. Vì UTF-8 được sử dụng trên hầu hết các nền tảng Unix, việc bỏ qua tùy chọn ``encoding`` khi mở các tệp UTF-8 (ví dụ: JSON, YAML, TOML, Markdown) là một lỗi rất phổ biến. Ví dụ::

   # BUG: "rb" mode or encoding="utf-8" should be used.
   with open("data.json") as f:
       data = json.load(f)

Để tìm loại lỗi này, một ``EncodingWarning`` tùy chọn được bổ sung. Nó được phát ra khi :data:`sys.flags.warn_default_encoding <sys.flags>` là true và mã hóa mặc định dành riêng cho locale được sử dụng.

Tùy chọn ``-X warn_default_encoding`` và :envvar:`PYTHONWARNDEFAULTENCODING` được bổ sung để bật cảnh báo.

Xem :ref:`io-text-encoding` để biết thêm thông tin.

Các tính năng mới liên quan đến Type Hints
==========================================

Phần này trình bày các thay đổi lớn ảnh hưởng đến :pep:`484` type hints và module :mod:`typing`.


PEP 604: Toán tử hợp kiểu mới
-----------------------------

Một toán tử hợp kiểu mới đã được giới thiệu, cho phép sử dụng cú pháp ``X | Y``. Cú pháp này cung cấp cách diễn đạt rõ ràng hơn cho “kiểu X hoặc kiểu Y” thay vì sử dụng :class:`typing.Union`, đặc biệt là trong type hint.

Trong các phiên bản Python trước đây, để áp dụng type hint cho các hàm nhận đối số thuộc nhiều kiểu, người ta sử dụng :class:`typing.Union`::

   def square(number: Union[int, float]) -> Union[int, float]:
       return number ** 2


Giờ đây, type hint có thể được viết ngắn gọn hơn::

   def square(number: int | float) -> int | float:
       return number ** 2


Cú pháp mới này cũng được chấp nhận làm đối số thứ hai cho :func:`isinstance` và :func:`issubclass`::

   >>> isinstance(1, int | str)
   True

Xem :ref:`types-union` và :pep:`604` để biết thêm chi tiết.

(Do Maggie Moss và Philippe Prados đóng góp trong :issue:`41428`, với các bổ sung của Yurii Karabas và Serhiy Storchaka trong :issue:`44490`.)


PEP 612: Biến đặc tả tham số
----------------------------

Hai tùy chọn mới để cải thiện thông tin được cung cấp cho các trình kiểm tra kiểu tĩnh về
:pep:`484`\ 's ``Callable`` đã được thêm vào mô-đun :mod:`typing`.

Đầu tiên là biến đặc tả tham số. Chúng được dùng để chuyển tiếp các kiểu tham số của một callable này sang một callable khác -- một mẫu thường thấy trong các hàm higher-order và decorator. Có thể tìm thấy các ví dụ sử dụng trong :class:`typing.ParamSpec`. Trước đây, không có cách dễ dàng nào để chú thích kiểu sự phụ thuộc của các kiểu tham số theo cách chính xác như vậy.

Tùy chọn thứ hai là toán tử ``Concatenate`` mới. Toán tử này được dùng cùng với các biến đặc tả tham số để chú thích kiểu cho một callable higher-order, trong đó thêm hoặc xóa các tham số của một callable khác. Có thể tìm thấy các ví dụ sử dụng trong :class:`typing.Concatenate`.

Xem :class:`typing.Callable`, :class:`typing.ParamSpec`,
:class:`typing.Concatenate`, :class:`typing.ParamSpecArgs`,
:class:`typing.ParamSpecKwargs`, và :pep:`612` để biết thêm chi tiết.

(Do Ken Jin đóng góp trong :issue:`41559`, với các cải tiến nhỏ của Jelle Zijlstra trong :issue:`43783`. PEP do Mark Mendoza biên soạn.)


PEP 613: TypeAlias
------------------

:pep:`484` giới thiệu khái niệm bí danh kiểu, chỉ yêu cầu chúng là các phép gán không chú thích ở cấp cao nhất. Sự đơn giản này đôi khi khiến các trình kiểm tra kiểu khó phân biệt giữa bí danh kiểu và các phép gán thông thường, đặc biệt khi có tham chiếu chuyển tiếp hoặc kiểu không hợp lệ. So sánh::

   StrCache = 'Cache[str]'  # a type alias
   LOG_PREFIX = 'LOG[DEBUG]'  # a module constant

Giờ đây, mô-đun :mod:`typing` có một giá trị đặc biệt là :data:`~typing.TypeAlias`, cho phép bạn khai báo bí danh kiểu một cách rõ ràng hơn::

   StrCache: TypeAlias = 'Cache[str]'  # a type alias
   LOG_PREFIX = 'LOG[DEBUG]'  # a module constant

Xem :pep:`613` để biết thêm chi tiết.

(Do Mikhail Golubev đóng góp trong :issue:`41923`.)

Các thay đổi khác về ngôn ngữ
=============================

* Kiểu :class:`int` có phương thức mới :meth:`int.bit_count`, trả về số lượng số 1 trong biểu diễn nhị phân của một số nguyên cho trước, còn được gọi là population count. (Được đóng góp bởi Niklas Fiekas trong :issue:`29882`.)

* Các view được trả về bởi :meth:`dict.keys`, :meth:`dict.values` và
  :meth:`dict.items` giờ đây đều có thuộc tính ``mapping`` cung cấp một
  đối tượng :class:`types.MappingProxyType` bao bọc dictionary ban đầu. (Được đóng góp bởi Dennis Sweeney trong :issue:`40890`.)

* :pep:`618`: Hàm :func:`zip` hiện có cờ ``strict`` tùy chọn, được dùng để yêu cầu tất cả các iterable có cùng độ dài.

* Các hàm builtin và extension nhận đối số integer hiện không còn chấp nhận
  :class:`~decimal.Decimal`\ s, :class:`~fractions.Fraction`\ s và các đối tượng khác chỉ có thể được chuyển đổi thành integer với mất mát (ví dụ: có phương thức :meth:`~object.__int__` nhưng không có
  phương thức :meth:`~object.__index__`). (Do Serhiy Storchaka đóng góp trong :issue:`37999`.)

* Nếu :func:`object.__ipow__` trả về :data:`NotImplemented`, operator sẽ chuyển đúng về :func:`object.__pow__` và :func:`object.__rpow__` như mong đợi. (Do Alex Shkop đóng góp trong :issue:`38302`.)

* Giờ đây, có thể sử dụng assignment expression không cần đặt trong dấu ngoặc đơn bên trong set literal và set comprehension, cũng như trong các chỉ mục của sequence (nhưng không phải slice).

* Các hàm có thuộc tính ``__builtins__`` mới, được dùng để tìm các symbol builtin khi một hàm được thực thi, thay vì tìm trong ``__globals__['__builtins__']``. Thuộc tính này được khởi tạo từ ``__globals__["__builtins__"]`` nếu có, nếu không thì từ builtins hiện tại. (Do Mark Shannon đóng góp trong :issue:`42990`.)

* Hai hàm dựng sẵn mới -- :func:`aiter` và :func:`anext` -- đã được thêm để cung cấp các đối tác bất đồng bộ của :func:`iter` và :func:`next`, tương ứng. (Do Joshua Bronson, Daniel Pope và Justin Wang đóng góp trong :issue:`31861`.)

* Các phương thức static (:deco:`staticmethod`) và phương thức class (:deco:`classmethod`) hiện kế thừa các thuộc tính phương thức (``__module__``, ``__name__``, ``__qualname__``, ``__doc__``, ``__annotations__``) và có thêm thuộc tính ``__wrapped__`` mới. Ngoài ra, các phương thức static hiện có thể được gọi như các hàm thông thường. (Do Victor Stinner đóng góp trong :issue:`43682`.)

* Các annotation cho những đích phức tạp (mọi đích ngoài các đích ``simple name`` được định nghĩa bởi :pep:`526`) không còn gây ra bất kỳ hiệu ứng runtime nào với ``from __future__ import annotations``. (Do Batuhan Taskaya đóng góp trong :issue:`42737`.)

* Các đối tượng class và module hiện tạo lười các dict annotation rỗng khi cần. Các dict annotation được lưu trong ``__dict__`` của đối tượng để tương thích ngược. Điều này cải thiện các best practice khi làm việc với ``__annotations__``; để biết thêm thông tin, vui lòng xem
  :ref:`annotations-howto`. (Do Larry Hastings đóng góp trong :issue:`43901`.)

* Các annotation bao gồm ``yield``, ``yield from``, ``await`` hoặc biểu thức được đặt tên hiện bị cấm dưới ``from __future__ import annotations`` do các side effect của chúng. (Do Batuhan Taskaya đóng góp trong :issue:`42725`.)

* Việc sử dụng các biến chưa liên kết, ``super()`` và những biểu thức khác có thể làm thay đổi quá trình xử lý bảng ký hiệu khi làm annotation hiện được chuyển thành không gây hiệu ứng dưới ``from __future__ import annotations``. (Do Batuhan Taskaya đóng góp trong :issue:`42725`.)

* Giá trị băm của các giá trị NaN thuộc cả kiểu :class:`float` và
  kiểu :class:`decimal.Decimal` hiện phụ thuộc vào identity của đối tượng. Trước đây, chúng luôn được băm thành ``0`` mặc dù các giá trị NaN không bằng nhau. Điều này có thể gây ra hành vi thời gian chạy bậc hai do các vụ va chạm hash quá mức khi tạo các dictionary và set chứa nhiều NaN. (Do Raymond Hettinger đóng góp trong :issue:`43475`.)

* Một :exc:`SyntaxError` (thay vì một :exc:`NameError`) sẽ được phát sinh khi xóa hằng số :const:`__debug__`. (Do Donghee Na đóng góp trong :issue:`45000`.)

* Các ngoại lệ :exc:`SyntaxError` hiện có các thuộc tính ``end_lineno`` và ``end_offset``. Chúng sẽ là ``None`` nếu chưa được xác định. (Do Pablo Galindo đóng góp trong :issue:`43914`.)

Các trường chỉ nhận đối số từ khóa
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

dataclasses hiện hỗ trợ các trường chỉ nhận đối số từ khóa trong phương thức __init__ được tạo tự động. Có một số cách để chỉ định các trường chỉ nhận đối số từ khóa.

Bạn có thể chỉ định rằng mọi field đều chỉ được truyền dưới dạng keyword:

.. code-block:: python

    from dataclasses import dataclass

    @dataclass(kw_only=True)
    class Birthday:
        name: str
        birthday: datetime.date

Cả ``name`` và ``birthday`` đều là các tham số chỉ được truyền dưới dạng keyword của phương thức __init__ được tạo tự động.

Bạn có thể chỉ định chỉ được truyền dưới dạng keyword cho từng field:

.. code-block:: python

    from dataclasses import dataclass, field

    @dataclass
    class Birthday:
        name: str
        birthday: datetime.date = field(kw_only=True)

Ở đây, chỉ ``birthday`` là chỉ được truyền dưới dạng keyword. Nếu đặt ``kw_only`` trên từng field, hãy lưu ý rằng có các quy tắc về việc sắp xếp lại field, vì các field chỉ được truyền dưới dạng keyword phải đứng sau các field không chỉ được truyền dưới dạng keyword. Xem tài liệu đầy đủ về dataclasses để biết chi tiết.

Bạn cũng có thể chỉ định rằng tất cả các field sau một marker KW_ONLY đều chỉ được truyền dưới dạng keyword. Đây có lẽ sẽ là cách sử dụng phổ biến nhất:

.. code-block:: python

    from dataclasses import dataclass, KW_ONLY

    @dataclass
    class Point:
        x: float
        y: float
        _: KW_ONLY
        z: float = 0.0
        t: float = 0.0

Ở đây, ``z`` và ``t`` là các tham số chỉ được truyền dưới dạng keyword, còn ``x`` và ``y`` thì không. (Do Eric V. Smith đóng góp trong :issue:`43532`.)

ssl
---

Mô-đun ssl yêu cầu OpenSSL 1.1.1 trở lên. (Do Christian Heimes đóng góp trong :pep:`644` và :issue:`43669`.)

Mô-đun ssl có hỗ trợ ban đầu cho OpenSSL 3.0.0 và tùy chọn mới
:const:`~ssl.OP_IGNORE_UNEXPECTED_EOF`. (Do Christian Heimes đóng góp trong :issue:`38820`, :issue:`43794`,
:issue:`43788`, :issue:`43791`, :issue:`43799`, :issue:`43920`,
:issue:`43789` và :issue:`43811`.)

Hàm không dùng nữa và việc sử dụng các hằng số không dùng nữa giờ đây sẽ dẫn đến một :exc:`DeprecationWarning`. :attr:`ssl.SSLContext.options` đã
:data:`~ssl.OP_NO_SSLv2` và :data:`~ssl.OP_NO_SSLv3` được đặt theo mặc định, vì vậy không thể cảnh báo về việc đặt lại cờ này. Phần
:ref:`các tính năng không dùng nữa <whatsnew310-deprecated>` có danh sách các tính năng không dùng nữa. (Do Christian Heimes đóng góp trong :issue:`43880`.)

Mô-đun ssl hiện có các thiết lập mặc định an toàn hơn. Các cipher không có forward secrecy hoặc MAC SHA-1 bị vô hiệu hóa theo mặc định. Security level 2 không cho phép sử dụng các khóa RSA, DH và ECC yếu với mức bảo mật dưới 112 bit.
:class:`~ssl.SSLContext` mặc định sử dụng phiên bản giao thức tối thiểu là TLS 1.2. Các thiết lập này dựa trên nghiên cứu của Hynek Schlawack. (Do Christian Heimes đóng góp trong :issue:`43998`.)

Các giao thức không được khuyến nghị SSL 3.0, TLS 1.0 và TLS 1.1 không còn được hỗ trợ chính thức. Python không chủ động chặn chúng. Tuy nhiên, các tùy chọn build của OpenSSL, cấu hình của bản phân phối, các bản vá của nhà cung cấp và các cipher suite có thể khiến quá trình handshake không thành công.

Thêm tham số *timeout* vào hàm :func:`ssl.get_server_certificate`. (Do Zackery Spytz đóng góp trong :issue:`31870`.)

Mô-đun ssl sử dụng heap-types và cơ chế khởi tạo nhiều giai đoạn. (Do Christian Heimes đóng góp trong :issue:`42333`.)

typing
------

Để xem các thay đổi lớn, hãy xem :ref:`new-feat-related-type-hints`.

Hành vi của :class:`typing.Literal` đã được thay đổi để tuân theo :pep:`586` và khớp với hành vi của các trình kiểm tra kiểu tĩnh được quy định trong PEP.

1. ``Literal`` hiện loại bỏ các tham số trùng lặp.
2. Các phép so sánh bằng giữa các đối tượng ``Literal`` hiện không còn phụ thuộc vào thứ tự.
3. Các phép so sánh ``Literal`` hiện tôn trọng kiểu dữ liệu. Ví dụ, trước đây ``Literal[0] == Literal[False]`` cho kết quả là ``True``. Hiện tại, kết quả là ``False``. Để hỗ trợ thay đổi này, bộ nhớ đệm kiểu được sử dụng nội bộ hiện hỗ trợ phân biệt các kiểu dữ liệu.
4. Các đối tượng ``Literal`` hiện sẽ phát sinh ngoại lệ :exc:`TypeError` trong quá trình so sánh bằng nếu bất kỳ tham số nào của chúng không phải là :term:`hashable`. Lưu ý rằng việc khai báo ``Literal`` với các tham số không thể băm sẽ không phát sinh lỗi::

      >>> from typing import Literal
      >>> Literal[{0}]
      >>> Literal[{0}] == Literal[{False}]
      Traceback (most recent call last):
        File "<stdin>", line 1, in <module>
      TypeError: unhashable type: 'set'

(Đóng góp bởi Yurii Karabas trong :issue:`42345`.)

Thêm hàm mới :func:`typing.is_typeddict` để xác định xem một annotation có phải là :class:`typing.TypedDict` hay không. (Đóng góp bởi Patrick Reader trong :issue:`41792`.)

Các lớp con của ``typing.Protocol`` chỉ khai báo các biến dữ liệu giờ đây sẽ phát sinh ``TypeError`` khi được kiểm tra bằng ``isinstance``, trừ khi chúng được trang trí bằng :deco:`~typing.runtime_checkable`. Trước đây, các phép kiểm tra này đều âm thầm thành công. Người dùng nên trang trí các lớp con của mình bằng decorator :deco:`!runtime_checkable` nếu muốn sử dụng runtime protocols. (Đóng góp bởi Yurii Karabas trong :issue:`38908`.)

Việc import từ các submodule ``typing.io`` và ``typing.re`` giờ đây sẽ phát ra
:exc:`DeprecationWarning`. Các submodule này đã không còn được khuyến nghị sử dụng kể từ Python 3.8 và sẽ bị xóa trong một phiên bản Python tương lai. Mọi thứ thuộc các submodule đó nên được import trực tiếp từ
:mod:`typing` thay vào đó. (Đóng góp của Sebastian Rittau trong :issue:`38291`.)

urllib.parse
------------

Các phiên bản Python trước Python 3.10 cho phép sử dụng cả ``;`` và ``&`` làm dấu phân cách tham số truy vấn trong :func:`urllib.parse.parse_qs` và
:func:`urllib.parse.parse_qsl`.  Do các mối lo ngại về bảo mật và để phù hợp với các khuyến nghị mới hơn của W3C, nội dung này đã được thay đổi để chỉ cho phép một khóa phân tách duy nhất, với ``&`` làm giá trị mặc định.  Thay đổi này cũng ảnh hưởng đến
:func:`!cgi.parse` và :func:`!cgi.parse_multipart` vì chúng sử dụng nội bộ các hàm bị ảnh hưởng.  Để biết thêm chi tiết, vui lòng xem tài liệu tương ứng của chúng. (Đóng góp bởi Adam Goldschmidt, Senthil Kumaran và Ken Jin trong :issue:`42967`.)

Sự hiện diện của các ký tự xuống dòng hoặc tab trong các phần của URL cho phép thực hiện một số dạng tấn công. Theo đặc tả WHATWG cập nhật :rfc:`3986`, các ký tự xuống dòng ASCII ``\n``, ``\r`` và ký tự tab ``\t`` sẽ bị parser trong :mod:`urllib.parse` loại bỏ khỏi URL, qua đó ngăn chặn những cuộc tấn công này. Các ký tự bị loại bỏ được kiểm soát bằng một biến cấp module mới ``urllib.parse._UNSAFE_URL_BYTES_TO_REMOVE``. (Xem :gh:`88048`)

Tối ưu hóa
==========

* Các hàm khởi tạo :func:`str`, :func:`bytes` và :func:`bytearray` hiện nhanh hơn (khoảng 30--40% đối với các đối tượng nhỏ). (Do Serhiy Storchaka đóng góp trong :issue:`41334`.)

* Mô-đun :mod:`runpy` hiện nhập ít mô-đun hơn. Thời gian khởi động lệnh ``python3 -m module-name`` trung bình nhanh hơn 1,4 lần. Trên Linux, ``python3 -I -m module-name`` nhập 69 mô-đun trên Python 3.9, trong khi trên Python 3.10, nó chỉ nhập 51 mô-đun (-18). (Do Victor Stinner đóng góp trong :issue:`41006` và :issue:`41718`.)

* Lệnh ``LOAD_ATTR`` hiện sử dụng cơ chế "per opcode cache" mới. Hiện lệnh này nhanh hơn khoảng 36% đối với các thuộc tính thông thường và 44% đối với slots. (Đóng góp của Pablo Galindo và Yury Selivanov trong :issue:`42093` và Guido van Rossum trong :issue:`42927`, dựa trên các ý tưởng ban đầu được triển khai trong PyPy và MicroPython.)

* Khi xây dựng Python với :option:`--enable-optimizations`, ``-fno-semantic-interposition`` hiện được thêm vào cả dòng biên dịch lẫn dòng liên kết. Điều này giúp tăng tốc quá trình build trình thông dịch Python được tạo bằng :option:`--enable-shared` với ``gcc`` lên đến 30%. Xem `bài viết này <https://developers.redhat.com/blog/2020/06/25/red-hat-enterprise-linux-8-2-brings-faster-python-3-8-run-speeds/>`_ để biết thêm chi tiết. (Đóng góp của Victor Stinner và Pablo Galindo trong
  :issue:`38980`.)

* Sử dụng mã quản lý output buffer mới cho :mod:`bz2` / :mod:`lzma` /
  :mod:`zlib` modules, và thêm hàm ``.readall()`` vào class ``_compression.DecompressReader``. Việc giải nén bz2 hiện nhanh hơn từ 1,09x đến 1,17x, giải nén lzma nhanh hơn từ 1,20x đến 1,32x, ``GzipFile.read(-1)`` nhanh hơn từ 1,11x đến 1,18x. (Đóng góp của Ma Lin, được Gregory P. Smith review, trong :issue:`41486`)

* Khi sử dụng annotations dạng chuỗi, các dict annotations cho các function không còn được tạo khi function được tạo nữa. Thay vào đó, chúng được lưu dưới dạng một tuple các chuỗi, và object function sẽ chuyển đổi chúng thành dict annotations một cách lazy khi cần. Tối ưu hóa này giảm một nửa thời gian CPU cần để định nghĩa một function có annotation. (Đóng góp của Yurii Karabas và Inada Naoki trong :issue:`42202`.)

* Các function tìm kiếm substring như ``str1 in str2`` và ``str2.find(str1)`` hiện đôi khi sử dụng thuật toán tìm kiếm chuỗi "Two-Way" của Crochemore & Perrin để tránh hành vi bậc hai trên các chuỗi dài. (Đóng góp của Dennis Sweeney trong :issue:`41972`)

* Thêm các micro-optimization vào ``_PyType_Lookup()`` để cải thiện hiệu năng tra cứu type attribute cache trong trường hợp phổ biến là cache hit. Điều này giúp trình thông dịch nhanh hơn trung bình 1,04 lần. (Đóng góp của Dino Viehland trong :issue:`43452`.)

* Các hàm tích hợp sau đây hiện hỗ trợ quy ước gọi vectorcall :pep:`590` nhanh hơn:
  :func:`map`, :func:`filter`, :func:`reversed`, :func:`bool` và :func:`float`. (Được đóng góp bởi Donghee Na và Jeroen Demeyer trong :issue:`43575`, :issue:`43287`, :issue:`41922`, :issue:`41873` và :issue:`41870`.)

* Hiệu năng của :class:`~bz2.BZ2File` được cải thiện bằng cách loại bỏ ``RLock`` nội bộ. Điều này khiến :class:`!BZ2File` không an toàn với thread khi có nhiều reader hoặc writer đồng thời, giống như các lớp tương đương trong :mod:`gzip` và
  :mod:`lzma` vốn luôn như vậy. (Được đóng góp bởi Inada Naoki trong :issue:`43785`.)

Không còn được khuyến nghị
==========================

* Hiện tại Python chấp nhận các literal số đứng ngay trước keyword, chẳng hạn như ``0in x``, ``1or x``, ``0if 1else 2``. Điều này cho phép các biểu thức gây nhầm lẫn và mơ hồ như ``[0x1for x in y]`` (có thể được hiểu là ``[0x1 for x in y]`` hoặc ``[0x1f or x in y]``). Kể từ bản phát hành này, một cảnh báo không còn được khuyến nghị sẽ được đưa ra nếu literal số đứng ngay trước một trong các keyword :keyword:`and`, :keyword:`else`,
  :keyword:`for`, :keyword:`if`, :keyword:`in`, :keyword:`is` và :keyword:`or`. Trong các bản phát hành tương lai, nó sẽ được thay đổi thành cảnh báo cú pháp, rồi cuối cùng thành lỗi cú pháp. (Được đóng góp bởi Serhiy Storchaka trong :issue:`43833`.)

* Bắt đầu từ bản phát hành này, sẽ có một nỗ lực phối hợp để bắt đầu dọn dẹp các ngữ nghĩa import cũ được giữ lại nhằm tương thích với Python 2.7. Cụ thể là,
  :meth:`!find_loader`/:meth:`!find_module` (được thay thế bằng :meth:`~importlib.abc.MetaPathFinder.find_spec`),
  :meth:`~importlib.abc.Loader.load_module` (được thay thế bằng :meth:`~importlib.abc.Loader.exec_module`),
  :meth:`!module_repr` (mà hệ thống import sẽ tự xử lý cho bạn), thuộc tính ``__package__`` (được thay thế bằng ``__spec__.parent``), thuộc tính ``__loader__`` (được thay thế bằng ``__spec__.loader``) và thuộc tính ``__cached__`` (được thay thế bằng ``__spec__.cached``) sẽ dần bị loại bỏ (cũng như các lớp và phương thức khác trong :mod:`importlib`).
  :exc:`ImportWarning` và/hoặc :exc:`DeprecationWarning` sẽ được đưa ra tùy theo trường hợp để giúp xác định mã cần được cập nhật trong quá trình chuyển đổi này.

* Toàn bộ namespace ``distutils`` không còn được khuyến nghị sử dụng và sẽ bị xóa trong Python 3.12. Hãy tham khảo phần :ref:`module changes <distutils-deprecated>` để biết thêm thông tin.

* Các đối số không phải số nguyên truyền cho :func:`random.randrange` không còn được khuyến nghị sử dụng. :exc:`ValueError` không còn được khuyến nghị sử dụng và sẽ được thay thế bằng :exc:`TypeError`. (Do Serhiy Storchaka và Raymond Hettinger đóng góp trong :issue:`37319`.)

* Các phương thức ``load_module()`` khác nhau của :mod:`importlib` đã được ghi nhận là deprecated kể từ Python 3.6, nhưng giờ đây cũng sẽ kích hoạt :exc:`DeprecationWarning`. Hãy sử dụng
  thay vào đó là :meth:`~importlib.abc.Loader.exec_module`. (Do Brett Cannon đóng góp trong :issue:`26131`.)

* :meth:`!zimport.zipimporter.load_module` đã bị deprecated để ưu tiên :meth:`~zipimport.zipimporter.exec_module`. (Do Brett Cannon đóng góp trong :issue:`26131`.)

* Việc hệ thống import sử dụng :meth:`~importlib.abc.Loader.load_module` giờ đây sẽ kích hoạt :exc:`ImportWarning` như
  :meth:`~importlib.abc.Loader.exec_module` được ưu tiên sử dụng. (Do Brett Cannon đóng góp trong :issue:`26131`.)

* Việc sử dụng :meth:`!importlib.abc.MetaPathFinder.find_module` và
  :meth:`!importlib.abc.PathEntryFinder.find_module` của hệ thống import giờ đây sẽ kích hoạt :exc:`ImportWarning` như
  :meth:`importlib.abc.MetaPathFinder.find_spec` và
  :meth:`importlib.abc.PathEntryFinder.find_spec` lần lượt được ưu tiên. Bạn có thể sử dụng

  :doc:`API cấp cao <../library/asyncio-api-index>` sau khi bị phản đối trong Python 3.8. Động lực đằng sau thay đổi này gồm nhiều nguyên nhân:

  2. Các hàm trong API cấp cao đã ngầm lấy event loop đang chạy của thread hiện tại kể từ Python 3.7. Trong hầu hết các trường hợp sử dụng thông thường, không cần truyền event loop vào API.
  3. Việc truyền event loop dễ gây lỗi, đặc biệt khi làm việc với các loop chạy trong những thread khác nhau.

  Lưu ý rằng API cấp thấp vẫn chấp nhận ``loop``. Xem :ref:`changes-python-api` để biết các ví dụ về cách thay thế mã hiện có.

  (Đóng góp bởi Yurii Karabas, Andrew Svetlov, Yury Selivanov và Kyle Stanley trong :issue:`42392`.)


Chuyển mã sang Python 3.10
==========================

Phần này liệt kê các thay đổi đã được mô tả trước đó và những bản sửa lỗi khác có thể yêu cầu bạn thay đổi mã.


Những thay đổi trong cú pháp Python
-----------------------------------

* Giờ đây, một cảnh báo ngừng sử dụng sẽ được phát ra khi biên dịch cú pháp trước đây hợp lệ nếu literal số nằm ngay trước một keyword (như trong ``0in x``). Trong các bản phát hành tương lai, cảnh báo này sẽ được đổi thành cảnh báo cú pháp, và cuối cùng thành lỗi cú pháp. Để loại bỏ cảnh báo và giúp mã tương thích với các bản phát hành tương lai, chỉ cần thêm một khoảng trắng giữa literal số và keyword theo sau. (Đóng góp của Serhiy Storchaka trong :issue:`43833`.)

.. _changes-python-api:

Các thay đổi trong Python API
-----------------------------

* Các tham số *etype* của :func:`~traceback.format_exception`,
  :func:`~traceback.format_exception_only`, và
  các hàm :func:`~traceback.print_exception` trong module :mod:`traceback` đã được đổi tên thành *exc*. (Đóng góp của Zackery Spytz và Matthias Bussonnier trong :issue:`26389`.)

* :mod:`atexit`: Khi Python thoát, nếu một callback được đăng ký với
  :func:`atexit.register` gặp lỗi, ngoại lệ của nó giờ đây sẽ được ghi nhật ký. Trước đây, chỉ một số ngoại lệ được ghi nhật ký, còn ngoại lệ cuối cùng luôn bị bỏ qua một cách im lặng. (Đóng góp của Victor Stinner trong :issue:`42639`.)

* :class:`collections.abc.Callable` generic hiện làm phẳng các tham số kiểu, tương tự như :data:`typing.Callable` hiện đang thực hiện. Điều này có nghĩa là ``collections.abc.Callable[[int, str], str]`` sẽ có ``__args__`` của ``(int, str, str)``; trước đây, giá trị này là ``([int, str], str)``. Mã truy cập các đối số thông qua :func:`typing.get_args` hoặc ``__args__`` cần tính đến thay đổi này. Ngoài ra, :exc:`TypeError` có thể được đưa ra đối với các dạng không hợp lệ khi tham số hóa :class:`collections.abc.Callable`, vốn có thể đã âm thầm bỏ qua trong Python 3.9. (Đóng góp của Ken Jin trong :issue:`42195`.)

* :meth:`socket.htons` và :meth:`socket.ntohs` hiện đưa ra :exc:`OverflowError` thay vì :exc:`DeprecationWarning` nếu tham số đã cho không vừa với số nguyên không dấu 16 bit. (Đóng góp của Erlend E. Aasland trong :issue:`42393`.)

* Tham số ``loop`` đã bị loại bỏ khỏi hầu hết các :mod:`asyncio`\  của
  :doc:`API cấp cao <../library/asyncio-api-index>` sau khi bị thông báo ngừng sử dụng trong Python 3.8.

  Một coroutine hiện có dạng như sau::

     async def foo(loop):
         await asyncio.sleep(1, loop=loop)

  Nên được thay thế bằng dạng này::

     async def foo():
         await asyncio.sleep(1)

  Nếu ``foo()`` được thiết kế cụ thể *không* chạy trong event loop đang chạy của thread hiện tại (ví dụ: chạy trong event loop của một thread khác), hãy cân nhắc sử dụng :func:`asyncio.run_coroutine_threadsafe` thay thế.

  (Đóng góp bởi Yurii Karabas, Andrew Svetlov, Yury Selivanov và Kyle Stanley trong :issue:`42392`.)

* Constructor :class:`types.FunctionType` hiện kế thừa builtins hiện tại nếu từ điển *globals* không có khóa ``"__builtins__"``, thay vì sử dụng ``{"None": None}`` làm builtins: hành vi giống như :func:`eval` và
  các hàm :func:`exec`. Việc định nghĩa một hàm bằng ``def function(...): ...`` trong Python không bị ảnh hưởng, globals không thể bị ghi đè bằng cú pháp này: hàm cũng kế thừa builtins hiện tại. (Đóng góp bởi Victor Stinner trong :issue:`42990`.)

Các thay đổi trong C API
------------------------

* Các hàm C API ``PyParser_SimpleParseStringFlags``, ``PyParser_SimpleParseStringFlagsFilename``, ``PyParser_SimpleParseFileFlags``, ``PyNode_Compile`` và kiểu được các hàm này sử dụng, ``struct _node``, đã bị loại bỏ do chuyển sang parser PEG mới.

  Mã nguồn hiện nên được biên dịch trực tiếp thành một code object bằng cách sử dụng, chẳng hạn, :c:func:`Py_CompileString`. Sau đó, code object thu được có thể được đánh giá bằng cách sử dụng, chẳng hạn, :c:func:`PyEval_EvalCode`.

  Cụ thể:

  * Một lệnh gọi đến ``PyParser_SimpleParseStringFlags`` theo sau bởi ``PyNode_Compile`` có thể được thay thế bằng cách gọi :c:func:`Py_CompileString`.

  * Không có cách thay thế trực tiếp cho ``PyParser_SimpleParseFileFlags``. Để biên dịch mã từ đối số ``FILE *``, bạn cần đọc tệp trong C và truyền buffer thu được cho :c:func:`Py_CompileString`.

  * Để biên dịch một tệp được chỉ định bằng tên tệp ``char *``, hãy mở tệp một cách tường minh, đọc tệp rồi biên dịch kết quả. Một cách để thực hiện việc này là sử dụng module :py:mod:`io` cùng với :c:func:`PyImport_ImportModule`, :c:func:`PyObject_CallMethod`,
    :c:func:`PyBytes_AsString` và :c:func:`Py_CompileString`, như phác thảo bên dưới. (Đã lược bỏ các khai báo và xử lý lỗi.)::

       io_module = Import_ImportModule("io");
       fileobject = PyObject_CallMethod(io_module, "open", "ss", filename, "rb");
       source_bytes_object = PyObject_CallMethod(fileobject, "read", "");
       result = PyObject_CallMethod(fileobject, "close", "");
       source_buf = PyBytes_AsString(source_bytes_object);
       code = Py_CompileString(source_buf, filename, Py_file_input);

  * Đối với các đối tượng ``FrameObject``, thành viên :attr:`~frame.f_lasti` hiện biểu diễn một offset wordcode thay vì một offset đơn giản vào chuỗi bytecode. Điều này có nghĩa là cần nhân số này với 2 để sử dụng với các API yêu cầu byte offset thay thế (chẳng hạn như :c:func:`PyCode_Addr2Line`). Cũng lưu ý rằng
    thành viên :attr:`!f_lasti` của các đối tượng ``FrameObject`` không được xem là ổn định: thay vào đó, hãy sử dụng :c:func:`PyFrame_GetLineNumber`.

Các thay đổi về C API
=====================

PEP 652: Duy trì Stable ABI
---------------------------

Stable ABI (Giao diện nhị phân ứng dụng) cho các module mở rộng hoặc việc nhúng Python hiện đã được định nghĩa một cách rõ ràng.
:ref:`stable` mô tả các đảm bảo về tính ổn định của C API và ABI, cùng với các phương pháp hay nhất để sử dụng Stable ABI.

(Do Petr Viktorin đóng góp trong :pep:`652` và :issue:`43795`.)

Tính năng mới
-------------

* Kết quả của :c:func:`PyNumber_Index` hiện luôn có kiểu chính xác là :class:`int`. Trước đây, kết quả có thể là một thể hiện của lớp con của ``int``. (Do Serhiy Storchaka đóng góp trong :issue:`40792`.)

* Thêm một thành viên :c:member:`~PyConfig.orig_argv` mới vào cấu trúc :c:type:`PyConfig`: danh sách các đối số dòng lệnh ban đầu được truyền vào tệp thực thi Python. (Do Victor Stinner đóng góp trong :issue:`23427`.)

* Các macro :c:func:`PyDateTime_DATE_GET_TZINFO` và
  :c:func:`PyDateTime_TIME_GET_TZINFO` đã được thêm để truy cập các thuộc tính ``tzinfo`` của :class:`datetime.datetime` và
  các đối tượng :class:`datetime.time`. (Do Zackery Spytz đóng góp trong :issue:`30155`.)

* Thêm một hàm :c:func:`PyCodec_Unregister` để hủy đăng ký hàm tìm kiếm codec. (Do Hai Shi đóng góp trong :issue:`41842`.)

* Hàm :c:func:`PyIter_Send` đã được thêm để cho phép gửi giá trị vào iterator mà không phát sinh ngoại lệ ``StopIteration``. (Do Vladimir Matveev đóng góp trong :issue:`41756`.)

* Thêm :c:func:`PyUnicode_AsUTF8AndSize` vào limited C API. (Do Alex Gaynor đóng góp trong :issue:`41784`.)

* Thêm hàm :c:func:`PyModule_AddObjectRef`: tương tự như
  :c:func:`PyModule_AddObject` nhưng không lấy một tham chiếu đến giá trị khi thành công. (Do Victor Stinner đóng góp trong :issue:`1635741`.)

* Thêm các hàm :c:func:`Py_NewRef` và :c:func:`Py_XNewRef` để tăng số lượng tham chiếu của một đối tượng và trả về đối tượng đó. (Do Victor Stinner đóng góp trong :issue:`42262`.)

* Các hàm :c:func:`PyType_FromSpecWithBases` và :c:func:`PyType_FromModuleAndSpec` hiện chấp nhận một lớp duy nhất làm đối số *bases*. (Do Serhiy Storchaka đóng góp trong :issue:`42423`.)

* Hàm :c:func:`PyType_FromModuleAndSpec` hiện chấp nhận slot ``tp_doc`` là NULL. (Do Hai Shi đóng góp trong :issue:`41832`.)

* Hàm :c:func:`PyType_GetSlot` có thể chấp nhận
  các :ref:`static type <static-types>`. (Do Hai Shi và Petr Viktorin đóng góp trong :issue:`41073`.)

* Thêm một hàm :c:func:`PySet_CheckExact` mới vào C-API để kiểm tra xem một đối tượng có phải là một instance của :class:`set` nhưng không phải là instance của một subtype hay không. (Do Pablo Galindo đóng góp trong :issue:`43277`.)

* Thêm :c:func:`PyErr_SetInterruptEx`, cho phép truyền một số hiệu signal để mô phỏng. (Do Antoine Pitrou đóng góp trong :issue:`43356`.)

* Limited C API hiện được hỗ trợ khi :ref:`Python được build ở chế độ debug <debug-build>` (nếu macro ``Py_DEBUG`` được định nghĩa). Trong limited C API, các hàm :c:func:`Py_INCREF` và :c:func:`Py_DECREF` hiện được triển khai dưới dạng các lời gọi hàm opaque, thay vì truy cập trực tiếp thành viên :c:member:`PyObject.ob_refcnt`, nếu Python được build ở chế độ debug và macro ``Py_LIMITED_API`` nhắm đến Python 3.10 hoặc mới hơn. Việc hỗ trợ limited C API ở chế độ debug trở nên khả thi vì cấu trúc :c:type:`PyObject` giống nhau trong chế độ release và debug kể từ Python 3.8 (xem :issue:`36465`).

  Limited C API vẫn chưa được hỗ trợ trong bản build đặc biệt :option:`--with-trace-refs` (macro ``Py_TRACE_REFS``). (Do Victor Stinner đóng góp trong :issue:`43688`.)

* Thêm hàm :c:func:`Py_Is(x, y) <Py_Is>` để kiểm tra xem đối tượng *x* có phải là đối tượng *y* hay không, tương tự như ``x is y`` trong Python. Đồng thời thêm
  các hàm :c:func:`Py_IsNone`, :c:func:`Py_IsTrue`, :c:func:`Py_IsFalse` để kiểm tra xem một đối tượng lần lượt có phải là singleton ``None``, singleton ``True`` hoặc singleton ``False`` hay không. (Do Victor Stinner đóng góp trong :issue:`43753`.)

* Thêm các hàm mới để điều khiển garbage collector từ mã C:
  :c:func:`PyGC_Enable()`,
  :c:func:`PyGC_Disable()`,
  :c:func:`PyGC_IsEnabled()`. Các hàm này cho phép kích hoạt, vô hiệu hóa và truy vấn trạng thái của bộ thu gom rác từ mã C mà không cần nhập mô-đun :mod:`gc`.

* Thêm cờ kiểu :c:macro:`Py_TPFLAGS_DISALLOW_INSTANTIATION` mới để không cho phép tạo các thể hiện của kiểu. (Do Victor Stinner đóng góp trong :issue:`43916`.)

* Thêm cờ kiểu :c:macro:`Py_TPFLAGS_IMMUTABLETYPE` mới để tạo các đối tượng kiểu bất biến: không thể đặt hoặc xóa các thuộc tính của kiểu. (Do Victor Stinner và Erlend E. Aasland đóng góp trong :issue:`43908`.)

Chuyển mã sang Python 3.10
--------------------------

* Macro ``PY_SSIZE_T_CLEAN`` giờ đây phải được định nghĩa để sử dụng
  các định dạng :c:func:`PyArg_ParseTuple` và :c:func:`Py_BuildValue` sử dụng ``#``: ``es#``, ``et#``, ``s#``, ``u#``, ``y#``, ``z#``, ``U#`` và ``Z#``. Xem :ref:`arg-parsing` và :pep:`353`. (Do Victor Stinner đóng góp trong :issue:`40943`.)

* Vì :c:func:`Py_REFCNT()` đã được thay đổi thành hàm static inline, ``Py_REFCNT(obj) = new_refcnt`` phải được thay thế bằng ``Py_SET_REFCNT(obj, new_refcnt)``: xem :c:func:`Py_SET_REFCNT()` (có từ Python 3.9). Để tương thích ngược, có thể sử dụng macro này::

      #if PY_VERSION_HEX < 0x030900A4
      #  define Py_SET_REFCNT(obj, refcnt) ((Py_REFCNT(obj) = (refcnt)), (void)0)
      #endif

  (Do Victor Stinner đóng góp trong :issue:`39573`.)

* Việc gọi :c:func:`PyDict_GetItem` khi chưa nắm giữ :term:`GIL` trước đây vẫn được cho phép vì lý do lịch sử. Hiện không còn được phép nữa. (Do Victor Stinner đóng góp trong :issue:`40839`.)

* ``PyUnicode_FromUnicode(NULL, size)`` và ``PyUnicode_FromStringAndSize(NULL, size)`` hiện sẽ raise ``DeprecationWarning``. Dùng :c:func:`PyUnicode_New` để cấp phát đối tượng Unicode mà không có dữ liệu ban đầu. (Do Inada Naoki đóng góp trong :issue:`36346`.)

* Cấu trúc private ``_PyUnicode_Name_CAPI`` của ``unicodedata.ucnhash_CAPI`` trong PyCapsule API đã được chuyển sang internal C API. (Do Victor Stinner đóng góp trong :issue:`42157`.)

* :c:func:`Py_GetPath`, :c:func:`Py_GetPrefix`, :c:func:`Py_GetExecPrefix`,
  :c:func:`Py_GetProgramFullPath`, :c:func:`Py_GetPythonHome` và
  các hàm :c:func:`Py_GetProgramName` hiện trả về ``NULL`` nếu được gọi trước
  :c:func:`Py_Initialize` (trước khi Python được khởi tạo). Hãy dùng phiên bản mới
  API :ref:`init-config` để lấy :ref:`init-path-config`. (Do Victor Stinner đóng góp trong :issue:`42260`.)

* :c:func:`PyList_SET_ITEM`, :c:func:`PyTuple_SET_ITEM` và
  Các macro :c:func:`PyCell_SET` không còn có thể được sử dụng làm l-value hoặc r-value. Ví dụ: ``x = PyList_SET_ITEM(a, b, c)`` và ``PyList_SET_ITEM(a, b, c) = x`` hiện sẽ gặp lỗi trình biên dịch. Điều này ngăn các lỗi như trong phép kiểm thử ``if (PyList_SET_ITEM (a, b, c) < 0) ...``. (Do Zackery Spytz và Victor Stinner đóng góp trong :issue:`30459`.)

* Các tệp API không giới hạn ``odictobject.h``, ``parser_interface.h``, ``picklebufobject.h``, ``pyarena.h``, ``pyctype.h``, ``pydebug.h``, ``pyfpe.h`` và ``pytime.h`` đã được chuyển đến thư mục ``Include/cpython``. Không được include trực tiếp các tệp này, vì chúng đã được include trong ``Python.h``; xem :ref:`api-includes`. Nếu đã include trực tiếp, hãy cân nhắc include ``Python.h`` thay thế. (Do Nicholas Sim đóng góp trong :issue:`35134`.)

* Sử dụng cờ kiểu :c:macro:`Py_TPFLAGS_IMMUTABLETYPE` để tạo các đối tượng kiểu bất biến. Không dựa vào :c:macro:`Py_TPFLAGS_HEAPTYPE` để quyết định một đối tượng kiểu có khả biến hay không; thay vào đó, hãy kiểm tra xem :c:macro:`Py_TPFLAGS_IMMUTABLETYPE` có được thiết lập hay không. (Do Victor Stinner và Erlend E. Aasland đóng góp trong :issue:`43908`.)

* Hàm không được lập tài liệu ``Py_FrozenMain`` đã bị xóa khỏi API giới hạn. Hàm này chủ yếu hữu ích cho các bản build Python tùy chỉnh. (Do Petr Viktorin đóng góp trong :issue:`26241`.)

Không còn được khuyến nghị
--------------------------

* Hàm ``PyUnicode_InternImmortal()`` hiện không còn được khuyến nghị và sẽ bị loại bỏ trong Python 3.12: hãy sử dụng :c:func:`PyUnicode_InternInPlace` thay thế. (Do Victor Stinner đóng góp trong :issue:`41692`.)

Đã xóa
------

* Đã loại bỏ các hàm ``Py_UNICODE_str*`` thao tác với các chuỗi ``Py_UNICODE*``. (Do Inada Naoki đóng góp trong :issue:`41123`.)

  * ``Py_UNICODE_strlen``: sử dụng :c:func:`PyUnicode_GetLength` hoặc
    :c:macro:`PyUnicode_GET_LENGTH`
  * ``Py_UNICODE_strcat``: sử dụng :c:func:`PyUnicode_CopyCharacters` hoặc
    :c:func:`PyUnicode_FromFormat`
  * ``Py_UNICODE_strcpy``, ``Py_UNICODE_strncpy``: sử dụng
    :c:func:`PyUnicode_CopyCharacters` hoặc :c:func:`PyUnicode_Substring`
  * ``Py_UNICODE_strcmp``: sử dụng :c:func:`PyUnicode_Compare`
  * ``Py_UNICODE_strncmp``: sử dụng :c:func:`PyUnicode_Tailmatch`
  * ``Py_UNICODE_strchr``, ``Py_UNICODE_strrchr``: sử dụng
    :c:func:`PyUnicode_FindChar`

* Đã loại bỏ ``PyUnicode_GetMax()``. Vui lòng chuyển sang các API mới (:pep:`393`). (Đóng góp bởi Inada Naoki trong :issue:`41103`.)

* Đã loại bỏ ``PyLong_FromUnicode()``. Vui lòng chuyển sang :c:func:`PyLong_FromUnicodeObject`. (Đóng góp bởi Inada Naoki trong :issue:`41103`.)

* Đã loại bỏ ``PyUnicode_AsUnicodeCopy()``. Vui lòng sử dụng :c:func:`PyUnicode_AsUCS4Copy` hoặc
  :c:func:`PyUnicode_AsWideCharString` (Đóng góp bởi Inada Naoki trong :issue:`41103`.)

* Đã xóa biến ``_Py_CheckRecursionLimit``: biến này đã được thay thế bằng ``ceval.recursion_limit`` của cấu trúc :c:type:`PyInterpreterState`. (Do Victor Stinner đóng góp trong :issue:`41834`.)

* Đã xóa các macro chưa được lập tài liệu ``Py_ALLOW_RECURSION`` và ``Py_END_ALLOW_RECURSION`` cùng trường ``recursion_critical`` của
  cấu trúc :c:type:`PyInterpreterState`. (Do Serhiy Storchaka đóng góp trong :issue:`41936`.)

* Đã xóa hàm chưa được lập tài liệu ``PyOS_InitInterrupts()``. Việc khởi tạo Python vốn đã ngầm cài đặt các signal handler: xem
  :c:member:`PyConfig.install_signal_handlers`. (Do Victor Stinner đóng góp trong :issue:`41713`.)

* Xóa hàm ``PyAST_Validate()``. Không thể xây dựng đối tượng AST (kiểu ``mod_ty``) bằng C API công khai nữa. Hàm này vốn đã bị loại khỏi C API giới hạn (:pep:`384`). (Do Victor Stinner đóng góp trong :issue:`43244`.)

* Xóa tệp header ``symtable.h`` và các hàm chưa được lập tài liệu:

  * ``PyST_GetScope()``
  * ``PySymtable_Build()``
  * ``PySymtable_BuildObject()``
  * ``PySymtable_Free()``
  * ``Py_SymtableString()``
  * ``Py_SymtableStringObject()``

  Hàm ``Py_SymtableString()`` vô tình từng là một phần của ABI ổn định nhưng không thể được sử dụng, vì tệp header ``symtable.h`` bị loại khỏi limited C API.

  Thay vào đó, hãy sử dụng module Python :mod:`symtable`. (Do Victor Stinner đóng góp trong :issue:`43244`.)

* Loại bỏ :c:func:`PyOS_ReadlineFunctionPointer` khỏi các header của limited C API và khỏi ``python3.dll``, thư viện cung cấp ABI ổn định trên Windows. Vì hàm này nhận một đối số ``FILE*``, không thể đảm bảo tính ổn định ABI của nó. (Do Petr Viktorin đóng góp trong :issue:`43868`.)

* Loại bỏ các tệp header ``ast.h``, ``asdl.h`` và ``Python-ast.h``. Các hàm này không được ghi lại tài liệu và bị loại khỏi limited C API. Hầu hết các tên được định nghĩa bởi những tệp header này không có tiền tố ``Py``, nên có thể gây xung đột tên. Ví dụ, ``Python-ast.h`` định nghĩa một macro ``Yield``, xung đột với tên ``Yield`` được sử dụng bởi header ``<winbase.h>`` của Windows. Thay vào đó, hãy sử dụng module Python :mod:`ast`. (Do Victor Stinner đóng góp trong :issue:`43244`.)

* Loại bỏ các hàm compiler và parser sử dụng kiểu ``struct _mod``, vì public AST C API đã bị loại bỏ:

  * ``PyAST_Compile()``
  * ``PyAST_CompileEx()``
  * ``PyAST_CompileObject()``
  * ``PyFuture_FromAST()``
  * ``PyFuture_FromASTObject()``
  * ``PyParser_ASTFromFile()``
  * ``PyParser_ASTFromFileObject()``
  * ``PyParser_ASTFromFilename()``
  * ``PyParser_ASTFromString()``
  * ``PyParser_ASTFromStringObject()``

  Các hàm này không được ghi lại tài liệu và bị loại khỏi limited C API. (Do Victor Stinner đóng góp trong :issue:`43244`.)

* Loại bỏ tệp header ``pyarena.h`` cùng các hàm:

  * ``PyArena_New()``
  * ``PyArena_Free()``
  * ``PyArena_Malloc()``
  * ``PyArena_AddPyObject()``

  Các hàm này không được ghi chép tài liệu, bị loại khỏi C API giới hạn và chỉ được compiler sử dụng nội bộ. (Do Victor Stinner đóng góp trong :issue:`43244`.)

* Thành viên ``PyThreadState.use_tracing`` đã bị loại bỏ để tối ưu hóa Python. (Do Mark Shannon đóng góp trong :issue:`43760`.)


Tính năng bảo mật đáng chú ý trong 3.10.7
=========================================

Việc chuyển đổi giữa :class:`int` và :class:`str` trong các cơ số khác 2 (nhị phân), 4, 8 (bát phân), 16 (thập lục phân) hoặc 32, chẳng hạn như cơ số 10 (thập phân), giờ đây sẽ phát sinh :exc:`ValueError` nếu số chữ số ở dạng chuỗi vượt quá một giới hạn, nhằm tránh các cuộc tấn công từ chối dịch vụ tiềm ẩn do độ phức tạp thuật toán. Đây là biện pháp giảm thiểu cho :cve:`2020-10735`. Có thể cấu hình hoặc tắt giới hạn này bằng biến môi trường, cờ dòng lệnh hoặc các API :mod:`sys`. Xem tài liệu về :ref:`giới hạn độ dài chuyển đổi chuỗi số nguyên <int_max_str_digits>`. Giới hạn mặc định là 4300 chữ số ở dạng chuỗi.

Tính năng bảo mật đáng chú ý trong 3.10.8
=========================================

Mô-đun :mod:`!mailcap` không còn được khuyến nghị giờ đây từ chối chèn văn bản không an toàn (tên tệp, kiểu MIME, tham số) vào các lệnh shell. Thay vì sử dụng văn bản đó, mô-đun sẽ cảnh báo và xử lý như thể không tìm thấy kết quả khớp (hoặc đối với các lệnh kiểm thử, như thể bài kiểm thử thất bại). (Do Petr Viktorin đóng góp trong :gh:`98966`.)
